# Design decisions and known limits

## Differences from the course design

The 57 tables are unchanged. `sql/01_schema.sql` differs from the course design (written for MySQL
and used with phpMyAdmin; not part of this repository) in only four ways:

1. **Generated ids** for `booking_id`, `payment_id`, `point_log_id` (`AUTO_INCREMENT` /
   `GENERATED BY DEFAULT AS IDENTITY`). With plain `INT` the application would have to invent
   the next id, and `MAX(id)+1` collides when two customers book at once. `BY DEFAULT` (not
   `ALWAYS`) lets the sample data insert explicit ids; `02_sample_data.sql` then moves the PostgreSQL
   sequences past them.
2. **`app_config`**, a small 58th table for business-rule constants (hold minutes, points per
   baht, points expiry, business-day cutoff), so rules change without touching code.
3. Comments are in English; the design file keeps the original Thai comments.
4. **Extra indexes:** `idx_booking_status_expiry` (the hold-expiry sweep) and an index for every
   foreign key (see "Indexes" below).

## Composite key vs surrogate id + UNIQUE

Both give the same business guarantee: `UNIQUE` on the same columns rejects duplicates exactly
like a primary key does. The difference is how other tables reference the row.

| | composite key | id + UNIQUE |
|---|---|---|
| Child tables | carry every key column | carry one column |
| Joins | several `ON` conditions | one |
| Meaning | the key says what the row is | `ticket_id = 57` says nothing |
| Safety | cannot be forgotten, the PK enforces it | forgetting the `UNIQUE` silently allows duplicates |
| InnoDB | every secondary index repeats the wide PK | narrow PK, one extra unique index |

Rule of thumb used here:

* **Composite key** for tables whose identity *is* a pairing and that nothing references:
  `movie_genre`, `discount_branch`, `showtime_subtitle`, `branch_reward`.
* **id + UNIQUE** for tables that are referenced a lot, or whose key exceeds about three columns.
* If an id is added, the `UNIQUE` on the business key is mandatory.

Decision for this project: **keep the composite keys of the course design.**

| Table | Key | Referenced by | Verdict |
|---|---|---|---|
| `ticket` | 5 columns | `monthly_pass_usage` only | keep; the PK is the anti-double-selling guard that the tests and the race test prove |
| `showtime` | 4 columns | `ticket`, `showtime_subtitle` | acceptable; first candidate if an API needs a single showtime id |
| `seat` | 3 columns | `ticket` | keep; short enough |
| pairing tables | composite | nothing | keep |

Measured, not guessed: `benchmarks/ticket-key-design/` compares the composite key with a
`showtime_id` on 2.8 million tickets. Result: indexes shrink a lot (PostgreSQL primary-key index
-64%; on MySQL the secondary indexes shrink 36%), but the hot queries (seat map of a showtime, tickets of a
booking) are equally fast.

There is also an integrity cost the benchmark made visible. Today `ticket` shares `branch_id` and
`theatre_id` between its foreign keys to `showtime` and to `seat`, so a ticket **cannot** point to a
seat of another theatre. With a bare `showtime_id` the database no longer checks that; keeping the
guarantee needs `branch_id`/`theatre_id` in `ticket`, a `UNIQUE (showtime_id, branch_id, theatre_id)`
on `showtime` and a three-column foreign key, which gives back part of the saving and most of the
simplicity. The strongest argument for `showtime_id` is therefore not speed or size but
**rescheduling**: a showtime's date/time is part of its key today and the foreign keys have no
`ON UPDATE CASCADE`, so a showtime with tickets cannot be moved.

Switching `ticket`/`showtime` to ids would touch `monthly_pass_usage`, `sp_pay_booking`, the sample data
and many tests for identical behaviour, and move the schema further from the design presented in
class. Revisit it when another table starts referencing `ticket` (refunds, reviews) or when an API
passes showtime ids around.

## Indexes

PostgreSQL does not create an index for a foreign key automatically (MySQL/InnoDB does, which is
easy to forget when moving from the course version). Without
one, `DELETE FROM ticket WHERE booking_id = ...` (used by `sp_release_expired` and
`sp_cancel_booking`), the payment lookups and every join from a parent to its children scan the
whole child table. `sql/01_schema.sql` therefore ends with an index for each foreign key that
is not already covered by the leading columns of an existing index (54 of them).

To audit this on any PostgreSQL database (expected result: 0 rows):

```sql
SELECT c.conrelid::regclass AS table_name, c.conname
FROM pg_constraint c
WHERE c.contype = 'f'
  AND NOT EXISTS (SELECT 1 FROM pg_index i
                  WHERE i.indrelid = c.conrelid
                    AND (i.indkey::int2[])[0:cardinality(c.conkey) - 1] = c.conkey);
```

There is also `idx_booking_status_expiry (booking_status, booking_expire_datetime)` for
the expiry sweep. Very small lookup tables (e.g. `rate`, `role`) do not really need their
foreign-key indexes; they are included for uniformity and cost almost nothing.

## Why the clock is a parameter

Every procedure takes `p_now` instead of calling `NOW()`. Tests can then pin the clock
(`2026-11-05 13:01:00`) and check expiry, validity windows and "showtime already started"
deterministically. A real caller passes `NOW()`.

## Transactions and errors

* A procedure runs in the caller's transaction: any exception undoes the whole call (inside a
  `DO` or `BEGIN ... EXCEPTION` block it undoes just that block). No explicit `ROLLBACK` is needed
  and a procedure can safely be called inside a larger transaction.
* A failed insert still **consumes an identity value**, so booking ids can skip numbers after a
  rejected request. That is normal and harmless.

## Preventing double-selling

The primary key of `ticket` (branch, theatre, showtime date, showtime time, seat) is the actual
guard: two sessions inserting the same seat cannot both succeed, whatever the isolation level.
The procedure only translates the duplicate-key error into `Seat already taken for this showtime`.
`scripts/run-race-test.sh` fires N simultaneous sessions at one seat and checks for a single
winner and a single ticket row.

## Locks used

| Where | Lock | Why |
|---|---|---|
| `sp_pay_booking` | `SELECT ... FOR UPDATE` on the booking | two payments of the same booking serialise; the second sees `PAID` |
| `sp_pay_booking` | `FOR UPDATE` on the discount row | the usage-limit count cannot be overshot by concurrent payments |
| `sp_redeem_reward` | `FOR UPDATE` on the member row | two redemptions of the same member cannot both pass the balance check |
| `sp_cancel_booking` | `FOR UPDATE` on the booking | cancel and pay of the same booking cannot interleave |

## Behaviour that differs by design

* Paying an **expired** hold is refused with `Hold has expired` and changes nothing; the seats
  are freed by the next `sp_release_expired` or `sp_hold_seats` (which releases expired holds
  first). Freeing them inside the failed payment would need a commit, and an exception undoes
  everything the call did.
* `sp_hold_seats` releases expired holds itself, so a lapsed hold never blocks a seat.

## Known limits

* **Points are a ledger, not FIFO lots.** The balance ignores expired earned rows but keeps all
  redemptions, so heavy redemption after an expiry can under-count. A production system would
  consume earned rows oldest-first.
* **Monthly Pass `MIN_GAP_MINUTES`** exists in `member_type_condition` but is not enforced.
* **One Monthly Pass ticket per booking**, no mixing Monthly Pass and paid tickets in the same booking.
* No API or UI; the database is the product.
